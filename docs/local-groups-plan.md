# 本地共用群組：實作計畫

## 範圍與權限

- OIDC 僅負責身分驗證；群組、成員與權限由本站管理，不同步 Zitadel 群組。
- 已登入使用者可建立群組，建立者成為群組管理員；一人可加入多個群組。
- 管理員可更名群組、加入已登入過的使用者、調整角色及移除成員。最後一位管理員不可被移除或降級。
- 使用者以本站使用者 ID 加入群組，不因同 email 而合併本機／OIDC 帳號。
- 名單與店家菜單可屬於個人或單一群組。群組成員可讀取並選用開團；只有群組管理員可修改共用資料。
- 全部後端入口都必須檢查權限，包含子資源、照片辨識、確認套用，以及開團時建立快照。
- 既有資料維持私有。送餐地址與開團紀錄維持個人資料，不因群組成員資格而分享。
- 成員資格被移除後，不可再讀取或修改群組資料；已建立的個人團保留原快照，仍由原主辦人管理。
- 第一版不做群組刪除、邀請信、既有資料轉移、全站超級管理員或 Zitadel 角色對應。

## 分工與順序

### 契約與安全細節

- 「共用群組」與既有「開團」使用不同名稱及資源，避免權限混淆。
- 群組成員只有 `admin`／`member` 兩種角色；不新增全站管理員角色。
- 查找成員只接受完整 Email，限該群組管理員使用，不提供全站使用者清單。若同 Email 有多個身分，回傳可辨識的帳號種類及本站 ID，必須明確選擇，不自動合併。
- 新建資料選定個人或群組範圍後，第一版不允許修改範圍；避免更新資料時意外公開個人資料。
- 最後管理員檢查與成員更新必須在同一資料庫交易內完成，防止並行降級造成群組無管理員。
- 不把成員角色快取在登入 session：每次資料存取依目前成員關係授權。
- 匯入草稿綁定實際發起人及資料範圍；其他管理員也不可接手套用不屬於自己的草稿。

1. 先完成程式探索與 API 契約，再分派 backend 與 frontend subagent。
2. Backend 負責 Rust、migration、後端測試及 OpenAPI 定義；frontend 負責 React 與前端測試。
3. 主 agent 負責契約協調、整合、型別產生、驗收與文件；不自動 commit、push 或部署。

## 驗收矩陣

### 實作交接注意事項

- API 資源名稱使用 `/api/v1/sharing-groups`，資料範圍欄位使用 `sharingGroupId`，避免與既有開團 API 混淆。
- 名單／店家列表預設仍為個人資料；傳 `sharingGroupId` 選擇群組。開團前端需聚合可用個人及各群組資料。
- 群組成員 API 以 `userId` 作為加入／修改／移除識別鍵（其值就是本站 organizer ID）；成員回應以 `id` 表示。介面使用完整 Email 查找後確認加入，不提供全站帳號瀏覽，亦不以 Email 自動合併身分。
- 回應中的名單／店家附帶 `sharingGroupId`（可空）與 `canManage`；前端依此顯示群組唯讀畫面，但後端仍逐次授權。
- 目前 vendor 有 `(organizer_id, name_key)` 唯一限制，migration 必須改成個人／群組各自命名空間，同時保留所有 menu_items 與外鍵。
- 讀取共用 aggregate 時必須保留真正的 creator/owner ID，不可用呼叫者 ID 重建。
- 權限 SQL 必須是「個人且 owner 相符」或「群組且有資格」，不可讓群組資料 creator 繞過成員資格。
- AI apply 直接呼叫交易 helper，不能只檢查 HTTP 或普通 repository；包含隱式同名 vendor matching、使用者編輯 accepted target IDs、rollback 與草稿範圍。
- 同一個人開團可混用有權讀取的不同範圍名單／店家，不新增不必要的同群組限制。

| 操作 | 個人擁有者 | 群組管理員 | 群組成員 | 非群組成員 |
|---|---|---|---|---|
| 讀取自己的個人名單／菜單 | 允許 | 不因群組角色取得權限 | 不因群組角色取得權限 | 不因群組角色取得權限 |
| 讀取／開團選用群組資料 | 需有群組資格 | 允許 | 允許 | 拒絕 |
| 新增／修改／刪除群組資料 | 需為群組管理員 | 允許 | 拒絕 | 拒絕 |
| 照片匯入到群組 | 需為群組管理員 | 允許 | 拒絕 | 拒絕 |
| 管理群組成員 | 需為群組管理員 | 允許，保護最後管理員 | 拒絕 | 拒絕 |
| 存取其他主辦人的團 | 拒絕 | 拒絕 | 拒絕 | 拒絕 |

公開點餐連結的既有能力不變：持有連結者可依原流程點餐，但不因此取得管理資料的權限。
